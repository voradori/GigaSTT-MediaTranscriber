# Как работает текущий срез

Этот документ описывает проверенную реализацию и причины выбора. Текущие задачи — в [ROADMAP.md](ROADMAP.md); план там не означает работающую функцию.

## Путь файла

1. `setup.cmd` один раз получает актуальный Windows-релиз GigaSTT с GitHub, проверяет SHA-256 архива и скачивает модели распознавания и пунктуации в `tools/` и `models/`. Обе папки исключены из Git. Проверенный на этой машине релиз — GigaSTT 2.21.0. Загрузка пунктуации проверена отдельным запуском на коротком синтетическом WAV.
2. Пользователь кладёт запись в `input/` и запускает `transcribe.cmd` для всех файлов либо передаёт имя файла/папки внутри `input/`. `youtube.cmd` принимает ссылку, скачивает аудио через `yt-dlp` и передаёт точные пути полученных файлов в следующие этапы; сеть нужна для YouTube. Если установлена pyannote Community-1, обе команды после STT вызывают диаризацию на том же выбранном наборе. Для MP4 `ffmpeg` копирует первую аудиодорожку в временный `extracting.m4a`, не меняя исходное видео; после успешной обработки временный файл удаляется.
3. Windows CLI GigaSTT распознаёт файл на CPU с `--offline`, применяет локальную модель пунктуации и пишет исходный JSON в `output/transcripts/<путь файла в input/>/raw.json`. ITN пока отключена. Процесс GigaSTT завершается после каждого файла; постоянного сервера нет.
4. Скрипт сопоставляет оформленный текст со словами и таймкодами raw-экспорта и создаёт `transcript.json` и строки `(м:сс) Текст...` в `transcript.txt`. Он делит строки на паузах, после конечных знаков и по ограничению длины. Если текст модели не удаётся однозначно сопоставить со словами, используются исходные слова без оформления. Если все три результата уже есть и оба JSON читаются, файл пропускается; повреждённый готовый результат блокируется для ручной проверки без перезаписи.
5. При установленной модели локальная Community-1 получает тот же выбранный набор после STT и сопоставляет временные отрезки голосов с готовыми словами. Отдельный `diarize.cmd` оставлен для уже готовых транскриптов. Для WebM сначала создаётся временный WAV 16 кГц; после прохода он удаляется. Исходные результаты не меняются: рядом создаются `diarization.json`, `transcript.speakers.json` и `transcript.speakers.txt`. Готовый `diarization.json` можно повторно использовать для изменения правил сопоставления без нового запуска модели.

Транскрипция не требует Codex, LLM или Docker. `summary.md` — отдельная будущая работа агента по запросу, а не часть этого запуска. Работа при физически отключённой сети ещё не проверялась; `--offline` запрещает сетевую загрузку во время распознавания.

Сведение команд проверено локально на выборе файла и пропуске уже готового результата с Unicode-именем, а передача точных путей YouTube проверена без сетевой загрузки. Полный новый YouTube-проход вместе с pyannote на этой машине не проверен: локальная модель и `.venv` здесь отсутствуют.

## Проверено на этой машине

- RTX 4080, Docker Desktop и `ffmpeg` доступны, но выбранный Windows CLI работает на CPU; GPU и Docker в текущем пути не используются.
- Пять Telegram OGG длительностью 14–54 с и MP3 созвона длительностью 53:16 прошли через `transcribe.cmd`. Для MP3 распознавание заняло около 106 с. У каждого есть `raw.json`, `transcript.json`, `transcript.txt`.
- MP4 того же созвона (исходный файл 11,3 ГБ) прошёл целиком: аудиодорожка 53:19, общий проход с извлечением занял около 105 с. Временный аудиофайл после успеха отсутствует.
- Повторный запуск пропустил все готовые папки. Входные файлы для проверки были связаны жёсткими ссылками, без копирования большого видео и без изменения оригиналов.
- Сравнение пяти OGG с внешней расшифровкой показало сохранение основных мыслей и чисел, но худшую пунктуацию и деление на фразы; есть отдельные ошибки слов. Меток спикеров в результатах пока нет.
- Локальная пунктуация проверена отдельно на OGG и полном MP3 (53:16, около 100 с). На MP3 все 7051 распознанное слово и его таймкод совпали с первым прогоном; в оформленном тексте появились знаки. Разбиение выросло с 383 до 720 строк; некоторые знаки и границы всё ещё выглядят ошибочными. Старые результаты оставлены для сравнения.
- Сопоставление исходных MP3 и MP4 результатов дало 6927 совпавших слов в последовательности из примерно 7,1 тыс. (отношение совпадения 0,979), но MP4-аудио длиннее на 2,82 с, а медианный сдвиг совпавших таймкодов — 1,48 с. Это сравнение двух экспортов, не оценка точности относительно записи.
- Встроенная диаризация GigaSTT проверена через временный локальный сервер на 0–5 и 10–15 минутах созвона. На первом участке она выдала 10 различных меток, 49 переключений на 442 слова; на втором — 4 метки, 45 переключений на 673 слова, включая метку для одного слова. Сервер после каждого запроса завершён. Такое разделение нельзя выдавать пользователю как надёжные голоса. [Документация GigaSTT](https://github.com/ekhodzitsky/gigastt/blob/main/docs/api.md) также ограничивает файловую диаризацию примерно 30 минутами на запрос; полный созвон 53:16 не проходит этим путём напрямую.
- Повреждённый тестовый OGG дал код ошибки 1 и понятный `error.txt`; после замены только тестового входа повтор создал три результата и удалил прежнюю ошибку. Отдельная проба с повреждённым готовым JSON остановилась с кодом 1 и оставила его байты неизменными. Обычный повтор с исходными OGG/MP3/MP4 снова прошёл без изменений результатов. Большой файл после сбоя и прерывание процесса пока не проверяли.
- CUDA-образ GigaSTT 2.21.0 через Docker с доступной RTX 4080 обработал полную аудиодорожку MP4 (53:19). Распознавание заняло 106,5 с, весь запуск контейнера около 110 с против около 105 с у Windows CPU-пути. Лог подтвердил выбор CUDA provider с возможным fallback; фактическую долю работы на GPU отдельно не доказали. Практического ускорения в этом прогоне нет.
- Пять роликов плейлиста «Прямые трансляции» скачаны через `yt-dlp` как WebM и расшифрованы локально. Чистое время CPU по частям 1–5: 80,5; 105,3; 99,3; 110,5; 152,6 с. Суммарно около 9:08 на 4:28 аудио, без загрузки. Для каждого есть три результата. Повторный запуск `youtube.cmd` с той же ссылкой не скачал аудио повторно и пропустил готовые транскрипты.
- На другом Windows-устройстве Community-1 4.0.7 и PyTorch CUDA проверены на RTX 3060 Laptop 6 ГБ. Первая часть плейлиста длительностью 39:35 скачана без видео; её длительность совпала с сохранённым транскриптом с разницей 0,001 с. Диаризация заняла около 1:30 и нашла два голоса. После безопасного заполнения коротких разрывов метки получили 4821 из 4826 слов (99,9%); пять слов на границах голосов оставлены `UNKNOWN`. Качество самих переключений ещё требует прослушивания.
- На том же устройстве обработаны остальные четыре части первого плейлиста и все 224 расшифровки [второго плейлиста](https://www.youtube.com/playlist?list=PLVfLJFEB_hPXdvX5MP8B1Asd84HWQXfHz). Набор ID плейлиста и папки результатов совпал полностью. Для каждого ID скачана только WebM-аудиодорожка; расхождение её длительности с транскриптом не превысило 0,001 с. Повторное распознавание GigaSTT не запускалось.
- Итоговый пакет содержит 229 читаемых комплектов `diarization.json`, `transcript.speakers.json` и `transcript.speakers.txt`, без оставшихся временных WAV. Метки получили 215273 из 215475 слов (99,906%), 202 слова оставлены `UNKNOWN`. Повторный запуск проверил все комплекты и пропустил их без пересчёта модели. В семи записях найдено больше трёх голосовых меток, максимум семь; эти записи требуют прослушивания до смыслового объединения меток.

## Выбор технологий и границы

- **Принято: Windows CLI GigaSTT + локальные модели.** На реальных OGG, MP3 и MP4 он дал результат без постоянно работающего сервиса. CPU-скорости оказалось достаточно для первого удобного среза. `raw.json` хранит прямой экспорт движка, а производные файлы можно менять позже.
- **Принято: Python для пакетного запуска и форматов результата; `ffmpeg` только для видео.** Это обеспечивает один пользовательский `.cmd`, отдельную папку на файл и сохранение исходной записи.
- **Docker/CUDA не включены в рабочий путь.** Полный прогон показал около 110 с вместе с контейнером против около 105 с на CPU. Дополнительная сложность запуска пока не оправдана выигрышем; Docker остался только инструментом этой пробы.
- **Принято: `yt-dlp` для YouTube, как в `G:\MusicExtract`.** Берём только получение аудиодорожки и оставляем её в `input/`; музыкальные стадии не нужны. `youtube.cmd` и вложенные папки работают без LLM: имена берутся из метаданных YouTube с ID для однозначности. Обычные транскрипты лежат в `output/transcripts/`, промежуточные технические пробы — в `output/technical/`.
- **Встроенная диаризация GigaSTT не включена в пользовательский результат.** Два участка реального созвона показали дробление голосов и частые смены меток, а длинный файл упирается в лимит API. Для отдельного необязательного прохода выбран Community-1: он не повторяет STT, сохраняет собственный исходный JSON и создаёт отдельные версии транскрипта. Технический пакетный прогон 229 записей успешен, но пользовательское качество переключений ещё не принято.
- **Принято: встроенная локальная пунктуация GigaSTT для новых заданий.** Она даёт знаки без LLM, сети при запуске и отдельного сервиса. Качество разбиения остаётся открытым: вывод внешнего STT местами читается лучше, а старые `raw.json` и транскрипты нельзя переписывать ради оформления.

Пока не проверены работа без физической сети, сбои и восстановление на большом файле, созвоны 1–3 часа и пользовательское качество смен голосов. Проверка готового результата сейчас выявляет синтаксически повреждённые JSON, но не доказывает смысловую полноту расшифровки или правильность каждой смены говорящего.
